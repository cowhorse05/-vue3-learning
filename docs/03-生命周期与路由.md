# 03｜生命周期与路由

## 1. 生命周期只记业务上最常用的

```ts
const items = ref<Sandbox[]>([])
let timer: ReturnType<typeof setInterval> | undefined

onMounted(() => {
  void load()
  timer = setInterval(() => { void load() }, 10_000)
})
onUnmounted(() => { if (timer) clearInterval(timer) })
```

`setup` 建立逻辑；`onMounted` 在 DOM 挂载后运行；`onUpdated` 在更新后运行；`onUnmounted` 清理组件占用的资源。轮询、WebSocket、window 事件与第三方图表实例都应考虑清理。**页面第一次加载数据不必强制放 `onMounted`**：也可以用立即执行的 `watch`、路由数据逻辑等；只需保证触发时机与依赖明确。

Composable 把上述逻辑装进 `useXxx()`：

```ts
function useSandboxList(appID: Ref<string>) {
  const items = ref<Sandbox[]>([])
  const loading = ref(false)
  async function reload() { /* 根据 appID 取数并更新状态 */ }
  watch(appID, reload, { immediate: true })
  return { items, loading, reload }
}
```

如果把 `ref` 声明在函数内，每次调用可有独立状态；若在模块顶层声明，多个调用者可能共享同一个值。看 `useXxx` 时先判断状态究竟在哪里创建。

## 2. 路由是 URL → 页面组件的映射

```ts
const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/apps', name: 'apps', component: AppOverviewView },
    { path: '/apps/:appID', name: 'app-detail', component: AppDetailView },
    { path: '/:pathMatch(.*)*', redirect: '/apps' },
  ],
})
```

`<RouterView />` 是匹配到的组件出现的位置；`<RouterLink>` 生成页面链接。Router 不会自动帮你取 Sandbox 数据，页面依然要调用 API。

| URL 部分 | 示例 | 常用意义 |
| --- | --- | --- |
| 路径参数 `params` | `/apps/team-a` 中 `team-a` | 明确要看的资源 |
| 查询参数 `query` | `?status=Running&page=2` | 筛选、分页、排序 |
| Hash | `#...` | 页面片段或 hash 路由 |

```ts
const route = useRoute()
const router = useRouter()
const appID = computed(() => String(route.params.appID))
const status = computed(() => String(route.query.status ?? ''))
router.push({ name: 'app-detail', params: { appID: 'team-a' } })
```

`route` 表示当前路由信息；`router` 提供跳转方法。`push` 增加一条浏览历史；`replace` 替换当前记录，适合某些登录回跳或纠正 URL 场景。

## 3. 参数变化时组件可能被复用

从 `/apps/a` 进入 `/apps/b` 时，可能还是同一个 `AppDetailView` 实例。只在 `onMounted` 读取一次 `appID`，就会保留旧数据。可监听参数：

```ts
watch(
  () => route.params.appID,
  () => { void loadForCurrentApp() },
  { immediate: true },
)
```

这和服务端每次 HTTP 请求都新建一个 handler 调用的直觉不同。前端页面组件可以持续存在，URL 变化并不保证重新构造组件。

## 4. 嵌套路由与布局

```text
/apps/:appID                   AppDetailLayout
/apps/:appID/sandboxes         其内部 RouterView 显示 SandboxList
/apps/:appID/network-policy    其内部 RouterView 显示 PolicyEditor
```

祖先布局可以保持侧栏和应用标题，子路由只替换内容区。如果一个页面显示成空白，检查父组件是否有 `<RouterView />`。

## 5. 路由守卫与权限

```ts
router.beforeEach(async to => {
  if (to.meta.requiresAuth && !authStore.user) {
    await authStore.loadCurrentUser()
  }
  if (to.meta.requiresAuth && !authStore.user) {
    return { name: 'login', query: { redirect: to.fullPath } }
  }
})
```

这是用户体验与页面访问控制。浏览器代码可被用户改动；后端需要对每个敏感 API 独立核验身份、角色和 AppID 范围。路由上的 `meta.role = 'Admin'` 不是服务端授权证据。

## 6. history 与 hash 的部署差异

`createWebHistory()` 的 URL 如 `/apps/a`。用户直接刷新时，Web 服务收到 `GET /apps/a`；若它只按静态文件路径找文件，会返回 404。静态服务需要把前端页面路径回退到 `index.html`，同时**不能把真实 `/api/` 错误也无条件改成 HTML 200**。

`createWebHashHistory()` 的 URL 如 `/#/apps/a`，`#` 后面的片段不作为通常的 HTTP 路径发送给服务端，配置简单但 URL 不同。选择模式要和 Ingress / Nginx 的回退规则一致。

## 7. 路由与后端 API 最终如何对齐

前端页面路径：`/apps/team-a/sandboxes?status=Running`；Router 读取 `team-a` 和 `Running`；API 模块可能请求 `GET /api/v1/sandboxes?appID=team-a&status=Running`。**这两个 URL 的结构不要求完全一致**。后端必须自己检查当前用户是否能访问 `team-a`，不能因为它出现在前端 URL 就信任它。
